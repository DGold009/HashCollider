# Collision theory

This document explains the mathematics behind HashCollider. Notation: `H` is a hash
function with an *n*-bit output, `N = 2^n` is the number of possible digests, and `b` is the
*effective* (truncated) size used in an experiment.

## Hash functions

A hash function maps inputs of arbitrary length to fixed-length digests:

```text
H : {0,1}*  ->  {0,1}^n
```

It must be efficient to compute and deterministic. A *cryptographic* hash function must
additionally behave, as far as anyone can tell, like a random function - in particular it
must resist the three attacks below.

## Preimages

**Preimage resistance (one-wayness):** given a digest `h`, it is infeasible to find any `m`
with `H(m) = h`. The generic attack is exhaustive search, costing about `2^n` evaluations.

## Second preimages

**Second-preimage resistance:** given an input `m1`, it is infeasible to find a *different*
`m2` with `H(m2) = H(m1)`. The generic attack again costs about `2^n`: each candidate
matches the fixed target with probability `2^-n`.

HashCollider's `brute-force` method is exactly this generic attack against a *truncated*
digest: it fixes the first generated input as the target and searches for a second input
that matches it. Expected cost: `2^b` attempts.

## Collisions

**Collision resistance:** it is infeasible to find *any* pair `m1 != m2` with
`H(m1) = H(m2)`.

Collisions always *exist*: there are infinitely many inputs but only `2^n` outputs
(pigeonhole principle). Collision resistance is about the infeasibility of *finding* one.
Note the order of difficulty: an attacker free to choose both inputs has much more freedom
than one who must match a given target, which is why collision resistance is the weakest of
the three properties and the first to fail (as it did for MD5 and SHA-1).

A pair of *identical* inputs is not a collision - HashCollider counts such repeats as
duplicate inputs and ignores them.

## Birthday paradox

With 23 people in a room, the probability that two share a birthday exceeds 50%, although
there are 365 days. The reason is that `k` people form `k(k-1)/2` *pairs*, and the number of
pairs grows quadratically.

## Birthday bound

Model the hash as a uniformly random function onto `N` values. After `k` inputs, the
probability that all digests are distinct is

```text
P(no collision) = prod_{i=1}^{k-1} (1 - i/N)  ~  exp(-k(k-1) / (2N))
```

so

```text
P(collision after k inputs)  ~  1 - exp(-k(k-1) / (2N))
```

Useful consequences:

| Quantity | Value |
| --- | --- |
| k at which P ~ 39% | `k = sqrt(N) = 2^(n/2)` - the **birthday bound** |
| k at which P = 50% | `k ~ 1.1774 * sqrt(N)` (`sqrt(2 ln 2) * sqrt(N)`) |
| expected k until first collision | `E[k] ~ sqrt(pi N / 2) ~ 1.2533 * sqrt(N)` |
| guaranteed collision (pigeonhole) | `k = N + 1` distinct inputs |

HashCollider prints `sqrt(2^b)` as the birthday bound and `sqrt(pi/2 * 2^b)` as the expected
number of attempts. **Both are statistical expectations, not guarantees** - individual
searches often need noticeably fewer or more attempts (the distribution is wide; its standard
deviation is about `0.66 * sqrt(N)`).

The birthday search (HashCollider's default method) realises this bound: it stores every
digest `h -> m` in a dictionary and stops as soon as a new, *different* input maps to a
stored digest. Its memory use grows with the number of attempts, which is the practical
limit in Python (roughly 150 bytes per stored entry).

### Birthday vs. brute force

| Effective bits b | Birthday: expected attempts ~ 1.25 * 2^(b/2) | Brute force: expected attempts ~ 2^b |
| --- | --- | --- |
| 8 | 21 | 257 |
| 16 | 322 | 65,537 |
| 24 | 5,134 | 16,777,217 |
| 32 | 82,138 | 4,294,967,297 |

## Collision resistance

For an ideal *n*-bit hash, the best generic collision attack costs `~2^(n/2)`. The *collision
security* of a hash is therefore at most `n/2` bits: 128 bits for SHA-256, 80 bits for
SHA-1, 64 bits for MD5.

A hash is considered *broken* for collision resistance when an attack substantially faster
than `2^(n/2)` is known. MD5 (collisions in seconds) and SHA-1 (about 2^63 work for the 2017
collision) are broken in this sense. SHA-2 and SHA-3 are not.

## Effective hash size

The **effective hash size** `b` is the number of output bits that are actually compared. If
a system only compares the first `b` bits of a digest - a short ID, a truncated fingerprint,
a 32-bit checksum - its collision resistance is at most `2^(b/2)`, **regardless of how
strong the underlying hash is**.

## Truncation

HashCollider defines, for any algorithm `H` and `1 <= b <= n`,

```text
T_b(m) = the b most significant bits of H(m)
       = int.from_bytes(H(m)[: ceil(b/8)], "big") >> (8 * ceil(b/8) - b)
```

`T_b` is a new hash function with `2^b` outputs. Finding `m1 != m2` with
`T_b(m1) = T_b(m2)` is a collision of `T_b`, **not** of `H`:

```text
SHA-256(x)[:b bits] == SHA-256(y)[:b bits]    does NOT imply    SHA-256(x) == SHA-256(y)
```

Correct wording: *"A collision was found in the first 16 bits of SHA-256. This does not
constitute a collision in the full SHA-256 output."* The full digests remain different; the
experiment would work identically for any hash function, because it relies only on the small
size of the effective output space.

If `H` behaves like a random function, then `T_b` behaves like a random `b`-bit function, so
experiments on truncated hashes match the theory above very closely - you can check this
with `hashcollider benchmark`, whose `Obs/Exp` column should be close to 1.

## Computational complexity

At roughly 10^6 hashes per second (a Python loop on one core) and 10^9 hashes per second (a
fast optimised attacker, for comparison):

| Target | Generic work | Time at 10^6 H/s | Time at 10^9 H/s |
| --- | --- | --- | --- |
| 16-bit truncated collision | ~2^8 | instant | instant |
| 32-bit truncated collision | ~2^16 | ~0.1 s | instant |
| 48-bit truncated collision | ~2^24 | ~20 s (and GBs of memory) | instant |
| 64-bit truncated collision | ~2^32 | ~1.5 hours (hundreds of GB of memory) | seconds |
| MD5, generic birthday | ~2^64 | ~600,000 years | ~600 years |
| SHA-1, generic birthday | ~2^80 | ~4 * 10^10 years | ~4 * 10^7 years |
| SHA-256, generic birthday | ~2^128 | ~10^25 years | ~10^22 years |

The age of the universe is about 1.4 * 10^10 years. Full-size SHA-256 collisions are
therefore far beyond reach of generic search, which is why HashCollider refuses such
searches and works with reduced effective sizes instead. (Memory-efficient methods such as
Pollard's rho / distinguished points avoid the storage cost of the birthday table but not
the `2^(n/2)` time.)
